DOCUMENTATION 7 (Version 6)
Behavioral Anomaly Detection Model
This document describes the final state of Version 6, which introduced the core anomaly detection model for BehaviorGuard-AI. Version 6 moved the project from feature engineering (V5) to behavioral anomaly detection, using two complementary unsupervised techniques: HDBSCAN density-based clustering and Isolation Forest anomaly scoring.
The objective of V6 was to identify rare behavioral patterns in user activity logs by analyzing deviations from established behavioral clusters.
1. Objective of V6
The primary objective of Version 6 was to build a behavior-driven anomaly detection system capable of identifying suspicious user activity patterns without requiring labeled attack data. Unlike threshold-based anomaly detection used in earlier versions, V6 attempts to detect anomalies using unsupervised behavioral modeling.
The model should detect anomalies based on:
•	Deviations from historical behavioral baselines
•	Rare combinations of activity features
•	Abnormal login and device usage patterns
•	Unusual temporal behavior

2. Input Dataset
V6 uses the dataset generated in Version 5 (behavior_dataset_v5_features.csv). Each row represents one user’s activity during a one-hour window.
Property	Value
Rows	~3,366,264
Granularity	Hourly user activity window
Features	Behavioral + contextual features
Context Dimensions	Shift × Role Group
	
3. Behavioral Features Used for Modeling
Only behavioral deviation features were used for anomaly detection. These features collectively describe temporal, behavioral, and device-level activity patterns to capture deviations from historical behavior.
Feature	Description
z_logon	Z-score of login frequency
z_pcs	Z-score of device usage
logon_deviation	Difference between current login count and baseline
device_deviation	Deviation from typical device usage
device_ratio	Device usage relative to baseline
burst_score	Login burst intensity
hour_deviation	Difference from typical working hour
session_gap	Time since previous session
logon_logoff_ratio	Ratio between login and logout events
night_activity_flag	Indicator of night-time activity

4. Contextual Segmentation
Behavior was analyzed within contextual groups to reduce variance and ensure that users are compared only with behaviorally similar peers. Clustering was applied separately within each Shift × Role context.
Shift Segmentation:
Shift	Time Window
Day	09:00 – 16:00
Evening	17:00 – 21:00
Night	22:00 – 08:00
Note: Role groups were inherited from the V5 HR dataset integration.

5. Density-Based Clustering (HDBSCAN)
HDBSCAN was selected as the primary behavioral clustering algorithm due to its ability to detect clusters of varying density, automatically discover cluster numbers, natively detect noise points, and handle complex behavioral distributions.
Clustering Parameters Used:
•	min_cluster_size: 50
•	min_samples: 10
•	metric: euclidean
•	cluster_selection_method: eom
Feature values were scaled using RobustScaler to handle outliers effectively.

The clustering process discovered a large number of behavioral patterns across the organization.

7. Anomaly Definition
In the HDBSCAN framework, cluster = -1 indicates noise points. These points represent observations that do not belong to any dense behavioral cluster and were treated as behavioral anomalies.
•	Total anomalies detected: 213,628 observations
•	Anomaly rate: ≈ 6.34%
This rate falls within the typical range observed in user behavior anomaly detection systems (3–10%).
8. Behavioral Signature of Clusters
Analysis of cluster statistics showed that clusters correspond to distinct behavioral modes.
Cluster	Behavioral Characteristics
Cluster 0	High login deviation with moderate burst activity
Cluster 3	Lower login deviation with moderate session gaps
Cluster 5	Low burst activity with larger hour deviations
Cluster 17	High burst score with short session gaps
Noise Cluster (-1)	session_gap ≈ 17.1 hours

The noise cluster suggests many anomalies involve unexpected activity following long inactivity periods, a pattern commonly associated with account compromise or irregular access.



9. Isolation Forest Validation
To validate the clustering-based anomaly detection, an Isolation Forest was trained on the same behavioral feature space. Isolation Forest detects anomalies based on tree isolation depth, identifying points that are easy to separate from the rest of the data.
Isolation Forest Configuration:
•	n_estimators: 200
•	contamination: ≈ 0.06
•	random_state: 42

10. Model Agreement Analysis
The predictions from HDBSCAN and Isolation Forest were compared to understand model overlap.
	IF Normal	IF Anomaly
HDBSCAN Normal	2,969,208	183,428
HDBSCAN Anomaly	195,083	18,545
Interpretation:
•	18,545: Anomalies detected by both models (≈ 8.7% of HDBSCAN anomalies confirmed by IF).
•	183,428: Anomalies detected only by Isolation Forest.
•	195,083: Anomalies detected only by HDBSCAN.
This indicates the models detect fundamentally different types of anomalies.

11. Isolation Forest Score Comparison
Lower Isolation Forest scores indicate a stronger anomaly likelihood.
Group	Mean IF Score

This confirms that HDBSCAN anomalies tend to receive lower Isolation Forest scores, validating their anomalous nature.

13. Key Observations from V6
•	Observation 1: Behavioral anomalies rarely manifest as extreme values in individual features. Instead, they appear as rare combinations of otherwise normal feature values.
•	Observation 2: Density-based clustering successfully identifies low-density behavioral regions that represent unusual activity patterns.
•	Observation 3: Isolation Forest detects extreme feature values, whereas HDBSCAN detects rare behavioral combinations. The two methods capture different anomaly mechanisms.
•	Observation 4: Anomaly rates vary across organizational roles (e.g., IT Admin ~7.15%, Logistics ~6.72%, Software Engineering ~5.91%), suggesting certain roles naturally exhibit higher behavioral variability.
•	Observation 5: Day-shift activity showed a higher anomaly rate than night shift. Day shifts involve higher behavioral diversity, making clustering more difficult and increasing noise detection.

14. Performance Considerations
Due to the properties of both models, the recommended production architecture combines both approaches: HDBSCAN for offline behavioral discovery and Isolation Forest for real-time anomaly scoring.
Algorithm	Training Cost	Inference Speed	Use Case
HDBSCAN	High	Not suitable for streaming	Offline behavioral discovery
Isolation Forest	Moderate	Fast and scalable	Real-time anomaly scoring
